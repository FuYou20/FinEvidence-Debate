# 多智能体链路第一次真实运行问题与优化记录

## 对比范围

- 优化前运行：`data/runs/debate_20261016_205902.json`
- 优化后运行：`data/runs/debate_optimization_v2_attempt3.json`
- 辩题相同：传音控股在非洲市场的竞争优势是否具有持续性？
- 运行上限相同：1 轮辩论、每方每轮最多 1 条质疑、最多 1 项裁判复核、最多 2 次深入调查。

优化前没有接入逐调用监控，因此旧运行的调用数来自审计轨迹推导，总耗时来自当时进程观测；优化后的调用数、耗时和 Token 来自代码自动记录。二者不能伪装成严格实验，但足以定位瓶颈并验证调用链缩短。

## 第一次运行暴露的问题

1. 证据判断器选择 `web_search` 或 `rewrite_query` 后，还要额外调用一次 LLM 生成 Query；一次运行产生 8 次重复的 Query Rewrite 调用。
2. 裁判始终执行“初审 + 终审”两次模型调用，即使初审没有提出任何证据复核请求。
3. 裁判 Prompt 重复携带完整调查包，相同证据正文在辩论记录中出现 64 次，但只有 43 个唯一 evidence_id。
4. 观点质疑会重新发起检索，却没有携带原观点已经引用的证据。本轮没有重新搜到某条材料时，模型可能把“没有命中”误判成“原证据不存在”。
5. Dense Embedding 是单点故障。真实复跑曾连续两次在第一次查询向量调用时超时，单次等待约 62 秒并导致整场运行退出。
6. 旧运行没有逐模型调用耗时、Prompt 大小、Token、Embedding 和网页搜索耗时指标，无法精确解释慢在哪里。

## 实施的优化

### 1. 合并证据决策与 Query 生成

`EvidenceDecision` 新增 `next_query`。证据判断器在选择 `rewrite_query` 或 `web_search` 时直接返回下一条查询，业务代码不再调用独立 Query Rewrite 模型。

### 2. 裁判按需执行第二次调用

初审现在同时生成完整 `verdict_draft` 和可选 `verification_requests`：

- 没有关键证据需要复核：直接采用草稿，裁判只调用一次模型；
- 确有关键证据需要复核：执行证据调查后，再调用一次模型修正裁决。

### 3. 构造去重后的裁判上下文

裁判输入只保留最终观点、质疑与更新、调查摘要以及按 evidence_id 去重后的证据库。完整审计记录仍保存在 JSON/HTML 中，不用“删除审计信息”换取短 Prompt。

### 4. 保留被质疑观点的原始证据

`stance_research` 增加 `context_evidence_ids`。观点质疑进入调查 Agent 时，先从 EvidenceRegistry 还原原证据，再与新检索结果合并。这样可以区分：

- 原证据本身不存在；
- 原证据存在，但新增调查没有找到更多材料；
- 原证据存在，但真实性或覆盖范围仍有缺口。

### 5. Dense 故障时降级为 BM25

Embedding 发生连接或超时异常时，当前运行打开 Dense 熔断器，后续检索直接退化为 BM25，同时在运行指标中记录 `degraded_retrievals`、错误类型和熔断状态。降级运行不会被冒充为正常混合检索。

### 6. 增加全链路性能监控

运行记录现在包含：

- 每次 LLM 调用类型、耗时、Prompt 字符数和 Token；
- Embedding、联网搜索的调用次数、耗时和错误；
- Hybrid Retrieval、Web Search 和降级检索次数；
- 整体墙钟时间。

## 前后结果

| 指标 | 优化前 | 优化后 | 变化 |
|---|---:|---:|---:|
| LLM 调用总数 | 28（轨迹推导） | 18（真实记录） | -35.7% |
| 独立 Query Rewrite 调用 | 8 | 0 | -100% |
| 裁判调用 | 2 | 1 | -50% |
| 裁判上下文字符数 | 109,380 | 62,180 | -43.2% |
| 总运行时间 | 约 1,002 秒 | 838.34 秒 | 约 -16.3% |
| 优化后总 Token | 未记录 | 200,748 | 建立后续基线 |
| 优化后 LLM 累计耗时 | 未记录 | 808.81 秒 | 占墙钟时间约 96.5% |

优化后最大单次调用仍是裁判初审：约 172.17 秒、62,568 Prompt 字符、41,782 Token。因此下一轮优化重点不是继续增加功能，而是缩短裁判输入和证据判断输出。

## 质量回归观察

优化后真实运行中，两条观点质疑都带入了原观点证据再补充检索。正反双方均没有因为“新一轮搜索没命中”直接撤回观点，而是根据缺失的年份、季度、国家和价位段数据缩小结论边界，执行 `revise`。这证明上下文保留问题已经在真实链路中得到修复，但不代表观点事实本身已经获得完整原文核验。

## 可用于简历的表述

> 基于真实运行审计定位多智能体链路中的重复 Query Rewrite、裁判双调用、证据上下文重复和 Dense 单点故障；通过合并决策与查询生成、按需裁判终审、Evidence ID 去重及 BM25 降级，将同配置 Demo 的 LLM 调用由 28 次降至 18 次（-35.7%）、裁判上下文缩短 43.2%、端到端耗时降低约 16.3%，并补充逐调用 Token/耗时监控与上下文保留回归测试。
